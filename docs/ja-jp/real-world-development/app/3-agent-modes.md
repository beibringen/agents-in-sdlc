最初にプロジェクトに小さな機能を追加しました。より大規模な変更には、さらに堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業し、適切なものを適切な方法で構築できるように設計されています。このレッスンから数回にわたり、一般的なエージェント駆動型開発のプロセスを実践します。Issue から新機能を作成し、コードが正しく、機能が期待どおりに動作することを確認し、最後にプロジェクトへマージします。

> [!NOTE]
> 機能のワークフローを進める間は、同じセッションを使用します。通常は作業対象ごとに異なるセッションや PR を使いますが、ここでは主な概念に集中するため、一部を簡略化します。

このレッスンでは、次の作業を行います。

- GitHub Issue から新しいエージェントセッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザーキャンバスで機能を手動で検証します。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズし、MCP による検証を追加し、QA エージェントを作成して、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、利用者はカテゴリーとパブリッシャーでゲームを絞り込む必要があります。バックログの Issue には機能が記載されていますが、カテゴリーの組み合わせ方など、コーディング前に合意すべき詳細もあります。Plan モードで決定事項を整理し、Autopilot に範囲を明確にした実装を任せます。

## 背景

AI コーディングエージェントを開発フローに導入しても、基本は変わりません。むしろ、基本はさらに重要になります。多くの開発者は、次のような流れで作業します。

1. 必要な作業の詳細が記載された Issue を開きます。
2. 構築する内容の計画を作成します。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. pull request (PR) を作成します。
7. コードのレビューと継続的インテグレーションプロセスが成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや Organization によって異なりますが、多くの場合は上記の流れを変形したものです。

この標準的な方法に沿うことで、AI が生成したコードが要件を満たし、人間が作成したコードと同じレビューのプロセスを通るようにできます。

## セッションモード

**セッションモード**は、エージェントにどの程度の自律性を与えるかを制御します。プロンプトフィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更を提案し、次の作業に進む前にユーザーの入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。計画を実行する前に内容をレビューして承認します。
- **Autopilot**: エージェントが自律的に作業し、入力を待たずにコードを書き、テストを実行して、タスクが完了するまで反復します。

最初に Plan モードで計画を確認し、その後 Autopilot で実装します。

## Issue からセッションを開始する

開始する前に、星評価の PR がマージ済みで、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。既存の Issue **Allow users to filter games by category and publisher** を開きます。テンプレートから用意された Issue なので、新たに作成する必要はありません。
2. **New session** を選択し、更新済みの `main` を基にした **new working tree** を選びます。

    ![GitHub Copilot app の Issue ビューで、New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モードセレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは成功するのにセッションでは失敗する場合は、アプリの PATH またはバージョンマネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を検出できないという理由だけで npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチを確認できます。Issue から開始したため、Copilot は機能リクエストをすでにコンテキストとして持っています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、Issue の受け入れ条件と計画を照らし合わせます。カテゴリーとパブリッシャーによる絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認してください。複数カテゴリーをどのように組み合わせるか、一致するゲームがない場合にどうなるかなど、不明確な動作について話し合います。

計画には、プロジェクトの既存ツールを使った lint、ユニットテスト、E2E テスト、型チェックを含めます。フィルター機能の実装とテストに範囲を絞り、品質ワークフローを完了してから PR を作成します。計画の修正は承認前に依頼します。後で検証するときに使えるよう、Issue の URL と合意した追加事項を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan** (または使用中のバージョンで表示される同等の選択肢) を選択します。承認するとモードが自動で切り替わると思い込まず、現在のモードを確認してください。モード表示が **Autopilot** であることを確かめます。

Copilot が実装を始めます。確立した計画に沿ってコードを生成し、テストを実行しながら反復します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画をレビューしてください。依存関係が不足している、またはポートが競合していると報告された場合は、チェック完了と判断する前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードは、ほかのコードと同じようにマージ前にレビューします。コードを確認し、サイトを起動して問題がないか確認しましょう。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリーとパブリッシャーの組み合わせも含め、結果を Issue と承認した追加事項に照らし合わせます。変更が既存のリポジトリの指示に従っていることも確認します。
3. lint、ユニットテスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、影響するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカルサーバーを再利用する場合があります。テスト対象がこの worktree のサーバーであり、以前のレッスンで起動したサーバーではないことを確認します。

## 新機能を確認する

コードに問題がないように見えても、実際に動くか確認します。前と同じようにアプリを起動し、ブラウザーキャンバスでサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザーキャンバスでページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリーを選択し、結果が一致することを確認します。フィルターを解除してからパブリッシャーを選択し、結果がそのパブリッシャーに一致することを確認します。
4. カテゴリーとパブリッシャーを組み合わせ、Issue と承認した計画に照らして結果を確認します。複数カテゴリーに対応する場合は、合意した組み合わせ動作を確かめます。
5. 該当するゲームがない組み合わせを試し、空の状態を確認します。フィルターを解除またはリセットし、一覧全体が戻ることを確認します。
6. 確認が終わったら、次のプロンプトを使い、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンのためにセッションを保持する

フィルター機能の PR はまだ作成またはマージしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを使います。次はカスタム指示をフィルター機能のコードに適用し、スキルと QA の改善を追加してから、レッスン 8 で PR をまとめて作成してマージします。開発サーバーを停止した後はセッションをアイドル状態にしておき、次のレッスンで同じセッションに戻ります。

## まとめと次のステップ

さまざまなエージェントモードを使って機能を構築し、レビューしました。このレッスンでは、次の作業を行いました。

- GitHub Issue から新しいエージェントセッションを開始しました。
- **Plan** モードで要件を定義しました。
- **Autopilot** モードを使って新機能を実装しました。
- コードをレビューしました。
- ブラウザーキャンバスで機能を手動検証しました。
